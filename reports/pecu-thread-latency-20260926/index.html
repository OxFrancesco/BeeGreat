What is slowing it down

  1. Broad pool reads dominate. executePools calls getPools() before applying token filters and limit. Full hydration loads pool tuples, the token catalog, and prices. Asking for five pools does not restrict that work to five pools. The successful discovery invocation used 12.201s CPU out of 21.409s wall time.
  2. Liquidity starts with a fresh cache. The Worker creates a new cache for every liquidity_budget request. No persistent poolLocatorStore is supplied. Resolving the known pool can therefore reload the raw pool collection, followed by a probe quote and a second quote for the actual swap. Planning used 22.656s CPU out of 28.398s wall time. Exact substage attribution needs the existing RPC hook wired up.
  3. Parallel tool calls encounter a serial Worker. A module-level pending promise chains all Aero dispatches in each isolate. It is not an account-global queue, but unrelated requests handled by that isolate can delay each other. The initial failed pool read and quote reached terminal tool events together after 14.304s; the underlying Aero invocations took 7.545s and 6.604s. Record queue wait separately before replacing this with bounded concurrency.
  4. A predictable symbol error caused another model round. Map the supported Base WETH and USDC symbols to the canonical catalog before calling Sugar. Keep rejection for unknown ambiguous symbols. Do not solve this by weakening token validation.
  5. The agent took four trips to the model. Every generation used GPT-6 Sol, medium effort, through OpenRouter. Full model time was 29.667s; 25.638s of that preceded first model output. Streaming itself totaled 4.029s. All four requests returned 200, one attempt each. There is no provider retry or rate-limit evidence in this turn.
  6. The fallback route exposed a broad prompt. Input grew from 29,677 to 30,815 tokens. Later calls reported prompt-cache reads, so this was not four entirely uncached prompts. The broad catalog adds work, but its independent latency contribution is not measured. A confident DeFi family selection could narrow it. The classifier's original answer and confidence were discarded.
  7. The separate price probe and final prose pass are avoidable candidates. The model asked for a 0.01 ETH quote before the budget planner did its own quotes. It then spent 6.426s rewriting the completed preview. A typed liquidity workflow can choose the required reads and render the plan directly. Benchmark answer quality and successful plans before claiming a saving.

Three “stalled HTTP response” warnings occurred at the end, 23–80ms after model completion. They are real resource-cleanup defects to investigate, but their timing does not explain the preceding 95 seconds. Analytics launches one client and one flush per event after the turn, which creates a burst. The installed PostHog core already attempts to cancel write-response bodies, so the warning's owning request must be traced before blaming PostHog.

The main Durable Object used only 10ms CPU across its 95.317s invocation. Gateway setup took 38ms. This evidence points to Aero work and model round trips, not a 95-second gateway cold start. No Nansen, Convex, or Codex-container work appears in this turn. Internet delivery and browser rendering after the server's first text remain unmeasured.

Make the harness visible

The easiest change is to use events we already have. OpenCode v2 exposes events.subscribe() and replayable sessions.log({after, follow}). Its event definitions include execution start/end, tool input/call/progress/success/failure, retry scheduling and compaction. Pecu's observeText currently listens only for text delta/end events.

  • Forward real tool lifecycle events through the web stream. Show “Checking balances”, “Finding the pool”, or “Preparing the position” with elapsed time and an optional completed-step list. The first status can appear on server receipt. No invented progress percentage or model reasoning text is needed.
  • Add one root $ai_trace per turn, plus routing, runtime startup, model, tool, queue wait, RPC and delivery spans. Share opaque correlation IDs across Cloudflare, PostHog and browser timing events. Current received/completed events lack trace IDs, which forced timestamp correlation.
  • Wire Sugar's existing onRpcEvent. It already supplies operation, duration, attempt count, page count, item count and failover use without request arguments. Add cache hit/miss and queue timestamps alongside it. This is the shortest route to explaining the 21.5s pool read and 28.6s planner.
  • Record first model output separately from first reply text, first stream frame and first browser paint. Model output can be a tool call or reasoning event. Calling that user-visible time to first token hides this turn's 93.2-second silence.
  • Send completed spans while the run continues, and batch delivery under waitUntil. Today all generation/tool events were sent at 14:17:30.662, after the run finished. Preserve cursor-based replay and deterministic IDs for recovery.
  • Keep allowlisted OpenCode log attributes. Its logger exposes attributes and causes, but our adapter discards both. “Skipping invalid tool registration” is consequently impossible to identify from the current Cloudflare line. Preserve tool name, operation, error code, attempt and duration; omit credentials, chat content and tool payloads.

Fix the timestamp convention before trusting the waterfall. Our captured generation and tool events carry start timestamps. Current PostHog source calculates ordinary capture-event starts as timestamp − latency, while OTel events retain start timestamps. Emit terminal timestamps for ordinary capture events and keep explicit start/end fields, or adopt genuine OTel spans. Do not mark ordinary capture events as OTel just to shift the display. This source-level mismatch is confirmed; the authenticated cloud UI was unavailable in the preview, so its deployed rendering was not visually verified.

PostHog already has a trace timeline that renders nested and overlapping spans. A new dashboard is unnecessary for the basic breakdown. The installed Node SDK also exposes experimental startSpan/withSpan, disabled unless tracing is configured. That is an optional later integration requiring Workerd verification; extending the existing capture adapter is the smaller first change.

Use Jev for a bounded workflow

I read the TypeSafe skill, current documentation and the installed SDK. Pecu already batches route and family questions, uses a 2.5s timeout with no retries, and keeps explicit commands outside classification. The SDK defaults to jev-latest. The incident log only says fallback; it does not establish whether the cause was low confidence, invalid output, missing configuration or a deliberate bypass. Routing was finished at +0.279s, so classifier waiting was not the main delay.

  1. Separate tool scope from action certainty. An uncertain route currently discards even a confident family result. Retain a well-supported DeFi family for the reasoning fallback, with the existing all-tools escape hatch. Family selection changes visibility, never transaction authority.
  2. Ask branch-specific questions in the same request. For a known liquidity workflow, ask intent, token pair, funding token, amount-versus-fraction, whether a range was stated, and whether the request means a new pool or a position in an existing pool. Use explicit unknown outcomes. Code consumes only relevant answers.
  3. Select values; do the math in code. Parse candidate numbers, percentages and addresses from the message, let Jev choose their roles, then copy and validate the selected source values. Map “half” to 5,000 basis points and calculate against a fresh wallet balance deterministically. Known symbols resolve from the chain catalog.
  4. Dispatch only complete, validated workflows. A supported request can go to the liquidity planner without repeated model discovery and a prose rewrite. Missing range, ambiguous intent, unsupported tokens or uncertain arguments go to clarification or the reasoning model. Preserve the stored preview and explicit confirmation boundary.
  5. Measure routing quality. Record selected route/family, confidence and option probabilities, actual returned model version, request time, timeout/error category and fallback reason. Evaluate negation, hypothetical requests, multiple intents and contextual follow-ups. Choose thresholds from those results; do not lower 0.9 merely to increase fast-path coverage.

The TypeSafe function-calling cookbook supports closed-set dispatch; parallel questions avoid sequential classifier calls; candidate extraction keeps values grounded. These are design recommendations, not measured Pecu improvements.

Recommended order

First wire queue/RPC spans, real status events, trace IDs and correct timestamps. Then fix canonical token resolution, targeted pool discovery and reusable pool locators. Next replace the broad isolate queue with measured bounded concurrency and remove duplicate discovery/quote work. Finally evaluate a Jev-driven liquidity workflow and direct preview rendering. A prompt acknowledgement can be near instant; a verified live quote and multi-call plan still require measured network and compute time.
